# Правила работы с репозиторием VSM Moscow

## Назначение

Репозиторий развивается как многомодульный проект обучающего симулятора
проводника ВСМ. Сейчас реализован один модуль `Game/`, внутри которого уже
разделены Browser Game Client и authoritative Game Server. Внешний Platform
Server остаётся отдельной границей и не должен получать заготовки или общую
архитектуру без отдельной задачи.

## Перед началом работы

1. Прочитайте `README.md` и `Game/docs/user/README.md`.
2. Найдите ближайший `AGENTS.md` для изменяемого модуля.
3. Проверьте `git status` и не удаляйте чужие незавершённые изменения.
4. Уточните границы задачи и не переносите изменения между модулями без
   необходимости.

Актуальные требования находятся в `Game/docs/user/`. Рабочие инструкции
реализации находятся в `Game/docs/agent/`, а общерепозиторный процесс — в
`docs/agent/`. `Game/docs/backlog/` и `docs/backlog/` хранят неактуальные и
исторические материалы и не являются источником текущих требований.

## Модули

| Каталог | Назначение | Локальные инструкции |
| --- | --- | --- |
| `Game/` | Browser client и Game Server на Phaser 4, TypeScript и Vite | `Game/AGENTS.md` |

Когда появится новый модуль, добавьте его в эту таблицу и дайте ему собственные
инструкции и независимую команду проверки.

## Команды модулей

Корень не дублирует команды конкретных модулей. Установка, запуск и проверка
описываются в локальных `README.md`, `AGENTS.md` и `justfile` соответствующего
модуля. Корневой CI только объединяет эти независимые проверки.

Необязательные инструменты `just`, Pueue, `fd`, `rg` и `procs` описаны отдельно в
[`docs/agent/tools.md`](docs/agent/tools.md). Они помогают агентам, но не
являются требованиями к окружению участника.

## Общие правила разработки

- Делайте минимальное изменение в границах задачи.
- Не вводите пустые слои, универсальные framework-обёртки и интеграционные
  контракты до появления реального потребителя.
- Доменная логика игры должна оставаться обычным TypeScript-кодом без
  зависимости от Phaser, DOM и Vite. Подробности — в
  `Game/docs/user/project_direction.md`.
- Новые зависимости должны иметь конкретное назначение и точную версию.
- После законченного изменения запустите проверки затронутого модуля.
- Для визуальных изменений дополнительно проверьте приложение в браузере.
- Не коммитьте секреты, `node_modules/`, `dist/` и локальное состояние tools.

## Работа с Phaser 4

Работаем с Phaser 4. Перед изменениями в `Game/` прочитайте и примените
релевантный Phaser skill из набора
[`phaserjs/phaser/skills`](https://github.com/phaserjs/phaser/tree/master/skills):

- `scenes` — если меняете жизненный цикл сцены;
- `loading-assets` — если добавляете ассеты или меняете их загрузку;
- `animations` — если создаёте анимации;
- `physics-arcade` — если меняете коллизии;
- `tilemaps` — если работаете с Tiled или Phaser Tilemap;
- `input-keyboard-mouse-touch` — если меняете управление.

Для других подсистем Phaser выбирайте соответствующий skill из того же набора.
Skill служит руководством, а не доказательством наличия API в установленной
версии. Не используйте вызов, пока не убедитесь, что он есть в Phaser 4.2.1.
Перед добавлением нового вызова Phaser API сначала объясните, почему он
подходит для задачи, затем проверьте его в типах/исходниках установленного
пакета или официальной документации Phaser 4.

## Ветки и интеграция

`main` — основная ветка разработки и содержит запускаемое проверенное состояние.
Работа ведётся в короткоживущих `feature/*`, `fix/*`, `docs/*` и `chore/*`
ветках от `main` с последующим возвратом в `main`. Ветка `release` хранит
отобранные стабильные снимки для выпуска; новые изменения переносятся в неё из
проверенного `main`. Ветка `dev` не используется для новой работы. Полный
процесс и критерии переноса в `release` описаны в
[`docs/agent/workflow.md`](docs/agent/workflow.md).
