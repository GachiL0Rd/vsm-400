# Содержимое модалок текущего demo

**Версия документа:** 0.3.0  
**Статус:** Draft  
**Дата редакции:** 2026-09-27

## 1. Общий принцип

Модалка является детальным представлением существующего игрового объекта или документа.

Она не является отдельной доменной мини-игрой.

Server projection задаёт публичные значения и доступные actions, Client отвечает за визуальное размещение элементов.

## 2. Чек-лист приёмки вагона

Для demo инвентарная опись и checklist приёмки объединяются в один короткий документ.

### Шапка

```text
ПРИЁМКА ВАГОНА

Поезд: ______
Вагон: ______
Дата / время: ______
Сотрудник: ______
```

### Проверяемые пункты

| Объект | Проверяется | Значения |
|---|---|---|
| Связь с машинистом | вызов проходит, устройство отвечает | норма / неисправно / не проверено |
| Огнетушитель | на месте, чека/пломба, давление, корпус | норма / неисправно / не проверено |
| Климат-контроль | связь, температура, дым, давление | норма / неисправно / не проверено |
| Стоп-кран | наличие, пломба, состояние | норма / неисправно / не проверено |
| Санитарное состояние | салон/служебные зоны | норма / замечание / не проверено |

### Нижняя часть

```text
Замечание:
____________________________________

[ ] Вагон принят
Подпись: __________
```

В первой версии подпись может быть чисто presentation field без рукописного ввода.

### Важная семантика

Journal state хранит именно то, что указал игрок, а не автоматически копирует фактический state объекта.

Это позволяет различать:

```text
объект проверен и записан правильно
объект проверен, но записан неправильно
объект не проверен, но отмечен как норма
```

## 3. Огнетушитель

Модалка показывает объект крупным планом.

### Проверяемые элементы

- чека/пломба;
- манометр;
- маркировка/наклейка;
- состояние корпуса;
- визуальное повреждение, если оно присутствует.

### Интерактивные элементы

- снять чеку / подготовить, когда действие допустимо;
- возможно отдельное действие осмотра манометра/маркировки, если это потребуется gameplay;
- закрыть модалку.

Стрелка манометра является отдельным динамическим visual layer.

## 4. Климат-контроль

Минимальный экран:

```text
КЛИМАТ-КОНТРОЛЬ

Температура           21.8 °C
Давление салона       НОРМА
Датчик дыма           НОРМА

Связь                 УСТАНОВЛЕНА
Последнее обновление  14:32:08

[ ОБНОВИТЬ ДАННЫЕ ]
```

При ошибке связи:

```text
Связь                 ОШИБКА
Данные не обновлены

[ ПОВТОРИТЬ ]
```

`RefreshClimateData` является настоящим server-side action.

Желательно различать:

```text
actual system state
last publicly read panel state
```

чтобы данные могли устаревать или не обновляться при потере связи.

## 5. Стоп-кран

Модалка показывает:

- основание/слот;
- ручку;
- пломбу;
- текущее положение.

Пломба должна быть хорошо видна.

Ручка и основание визуально разделены, чтобы Client мог менять положение ручки независимо от background/base asset.

Минимальные состояния:

```text
seal: intact / broken
handle: normal / activated
```

Точная возможность возврата стоп-крана в исходное положение остаётся content rule и не должна определяться самой картинкой.

## 6. Билет пассажира

Билет программно заполняется поверх визуальной основы.

Минимальные поля:

```text
Пассажир
Маршрут (если используется)
Поезд
Дата
Время отправления
Вагон
Место
Уровень обслуживания
Тип документа
Маскированный номер документа
QR / визуальный код
```

Пример:

```text
БИЛЕТ

Иванов Сергей Петрович
Москва → Санкт-Петербург
Поезд: 752А
Дата: 27.09.2026
Отправление: 14:35
Вагон: 06
Место: 18
Класс: Комфорт
Документ: паспорт
**** 123456
```

Цена, гражданство, сборы и другие поля не добавляются без gameplay-потребности. Уровень обслуживания должен быть доступен игроку в билете либо через эквивалентный явно наблюдаемый источник, поскольку от него зависят ожидаемые услуги.

## 7. Паспорт / удостоверение личности

Используется раскрытый документ с программно заполняемыми полями.

Минимально:

```text
фото
фамилия
имя
отчество
дата рождения
серия/номер
```

Скрытые server-side признаки вроде `documentValid`, типа подделки или ожидаемого решения в public modal не передаются.

## 8. Связь с машинистом

Основное представление — объект на стене/в служебной зоне.

Для demo достаточно действий:

- проверить связь во время приёмки;
- выполнить предусмотренный сценарием доклад/вызов.

Если отдельная модалка понадобится, она должна быть простой и показывать только доступные команды/статус соединения.

## 9. Санитарное состояние

Отдельная модалка не обязательна.

Санитарные признаки существуют как наблюдаемые состояния зон/объектов и отражаются в журнале приёмки.


## 10. Точка выдачи еды и напитков

Для baseline не требуется отдельный художественно сложный объект или набор food assets.

Достаточно простой modal/service point:

```text
ОБСЛУЖИВАНИЕ

[ ВЗЯТЬ ЕДУ ]
[ ВЗЯТЬ НАПИТОК ]
```

Кнопки являются server-side actions и помещают соответствующий Item в единственный held slot игрока, если рука свободна.

Клиент может временно использовать текст/простые иконки. Посуда, упаковка и мусор в baseline не отображаются и не возвращаются.
