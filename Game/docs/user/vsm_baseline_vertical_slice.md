# Baseline vertical slice обучающего симулятора проводника ВСМ

**Версия документа:** 0.7.0
**Статус:** Draft / concrete demo baseline
**Дата редакции:** 2026-09-27

Baseline описывает минимальный объём систем и конкретного контента, достаточный для короткой полностью проходимой смены.

Он является подмножеством общей концепции из `vsm_conductor_game_concept.md` и должен читаться вместе с `implementation/`.

Наблюдаемое игровое поведение не определяет размещение доменной логики. В целевой архитектуре authoritative state, navigation, actions, NPC decisions и последствия находятся на Game Server; Browser Client визуализирует public projection и локальные ассеты.

## 1. Критерий готовности

Baseline считается рабочим, если игрок может:

1. появиться у назначенного вагона на исходном перроне;
2. забрать журнал приёмки из заданной точки перрона;
3. проверить основные объекты и санитарное состояние;
4. самостоятельно заполнить журнал и вернуть его в исходную точку до отправления;
5. после приёмки пройти отдельное окно посадки на исходной станции и начать поездку;
6. проходить последовательность поездок и остановок, принимая/высаживая пассажиров;
7. проверять документы пассажиров, учитывать уровень обслуживания и взаимодействовать с NPC;
8. столкнуться минимум с одной технической или пожарной ситуацией;
9. корректно либо некорректно отреагировать и получить последствия, включая возможное досрочное завершение;
10. завершить попытку и получить `safety`/`customerSatisfaction`, achievements и при guided-mode — обучающие hints.

## 2. Пространство

Для baseline достаточно:

- `carriage-main` с входной зоной/тамбуром, пассажирским салоном и служебной зоной;
- `platform-origin` для начальной приёмки;
- одного reusable `platform-standard` для обычных остановок;
- точек размещения основных систем и оборудования.

Перрон реализуется как временно подключаемый spatial region. Во время travel он неактивен/скрыт; анимация движения поезда и полноценная внешняя локация не требуются.

Server-side пространство представляется logical grid с cells/edges. Client получает только данные, необходимые для отображения.

Свободно перемещаются игрок, NPC и переносимые предметы. Стационарные панели и системы остаются привязанными к Level.

## 3. Базовое управление

Игрок умеет:

- задавать цель перемещения;
- выбирать доступное контекстное действие;
- открывать close-up/modal существующего объекта;
- держать один активный предмет;
- редактировать журнал;
- проверять документы пассажира;
- разговаривать/выбирать server-provided actions;
- пользоваться связью;
- ждать и ускорять игровое время, если режим/сценарий это разрешает.

Все игровые preconditions проверяются сервером.

## 4. Конкретные объекты текущего demo

Детальная схема находится в `implementation/interactables.md`.

### 4.1. Журнал приёмки

В начале смены находится на исходном перроне в настроенном anchor. Игрок должен забрать его, провести приёмку и вернуть журнал в ту же точку до отправления.

Содержит проверки:

- связь с машинистом;
- огнетушитель;
- климат-контроль;
- стоп-кран;
- санитарное состояние.

Игрок самостоятельно отмечает результат. Journal state не заполняется автоматически из фактического состояния мира.

Перед переходом к посадке журнал должен быть заполнен, отмечен как принятый и возвращён в исходный anchor. Сервер использует это как gate выхода из `preDeparture`. Некритические замечания допускают продолжение, а техническое значение `problem` по связи, огнетушителю, климату или аварийному тормозу считается критическим и завершает попытку через pre-departure terminal rule. Journal state при этом всё ещё остаётся самостоятельным решением игрока и не заполняется автоматически из фактического состояния вагона.

### 4.2. Огнетушитель

Один domain object используется во всех presentation contexts:

```text
на стене -> в руках -> close-up -> применение на пожаре
```

Проверяются:

- наличие/положение;
- чека/пломба;
- давление;
- корпус/повреждение;
- маркировка при необходимости.

Игрок может взять предмет, подготовить его и использовать на очаге пожара.

### 4.3. Климат-контроль

Панель показывает:

- температуру;
- давление салона;
- состояние датчика дыма;
- состояние связи;
- время последнего обновления.

Кнопка обновления является server-side action и одновременно проверяет связь с системой.

Допускается различать фактическое состояние системы и последние показания панели.

### 4.4. Стоп-кран

Минимально имеет:

- состояние пломбы;
- положение ручки.

Close-up позволяет визуально проверять и при разрешённых условиях изменять состояние.

### 4.5. Связь с машинистом

Стационарный элемент вагона.

Используется минимум для:

- проверки связи при приёмке;
- предусмотренных сценарием докладов/вызовов.

### 4.6. Точка обслуживания

Простой стационарный service point с modal:

```text
[ Взять еду ]
[ Взять напиток ]
```

Выдаёт один переносимый предмет в held slot. Отдельные запасы, посуда, упаковка и мусор в baseline не моделируются.

### 4.7. Санитарное состояние

Не имеет отдельной модалки. Загрязнения представлены накладываемыми runtime tiles/overlays на cells/локальных областях.

Для baseline они статичны: уборка не моделируется. Игрок должен заметить загрязнение и корректно отразить санитарное состояние в журнале.

## 5. Переносимые предметы

Baseline не требует общего inventory.

В руке находится максимум один предмет.

На текущий момент переносимы:

- журнал приёмки;
- огнетушитель;
- простая еда;
- простой напиток.

Игрок держит максимум один предмет. Еда/напиток берутся через простую service-point модалку; посуда и мусор не моделируются.

Пассажирские документы отображаются через interaction/modal и не обязаны становиться физическими предметами мира.

## 6. Документы пассажира

Во время посадки игрок получает доступ к:

- билету;
- паспорту/удостоверению личности.

Оба документа заполняются программно поверх клиентского визуального шаблона.

Игрок сравнивает наблюдаемые поля и принимает server-authoritative решение, например:

```text
admit passenger
reject passenger
```

Hidden признаки корректности, типа нарушения и ожидаемого результата остаются на сервере.

## 7. Пожар

Baseline содержит scripted пожар в салоне. Incident начинается через заданный Scenario интервал после фактического отправления и создаёт server-side fire source в разрешённой `failureLocation`. Игнорирование пожара при достижении критического порога завершает попытку через `fire-unsalvageable -> wagon-unsalvageable`.

Ключевой игровой цикл:

1. обнаружить публичный очаг `fire:<cellId>`;
2. осмотреть установленный огнетушитель либо взять его;
3. если огнетушитель уже в руке — кликнуть на игрока и открыть его inspection modal;
4. снять чеку в modal;
5. подойти к очагу;
6. применить подготовленный огнетушитель;
7. получить authoritative уменьшение fire state.

Первый field runtime использует конечное топливо и шаг `dt`. В упрощённом виде:

```text
fuel' = max(0, fuel - burnRate * dt * fire)
spreadGate = max(0, spreadGateThreshold - spreadFuelScale * fuel')
fire' = max(0, fire + growth * dt * fire - decay * dt
                 + neighbourTransfer * spreadGain * spreadGate
                 + source * dt)
```

Материал клетки задаёт `flammability`, growth/decay, запас топлива и параметры gate/transfer. Edge weights продолжают задавать пространственную связность. Это gameplay-модель, а не CFD.

Температура датчика (`mean(baseTemp + k*fire)`) относится к следующему climate-control срезу и пока не является частью baseline fire runtime.

## 8. Давление и климат

Давление является частью общей пространственной/системной модели, но baseline не требует физически точной симуляции.

Простой вариант:

- поле/состояние обновляется периодически;
- соседние клетки обмениваются значением через edge coefficients;
- источники/утечки и damping задают рост/затухание;
- панель климат-контроля показывает интерпретируемое публичное состояние.

Игрок может дополнительно получать косвенные признаки через NPC/звук/сценарий.

## 9. Пассажиры

Для одного рейса достаточно 2–3 пассажиров. Для демонстрации service logic желательно иметь представителей разных уровней обслуживания (`basic`, `comfort`, `business`) либо детерминированно распределять их Scenario.

Каждый пассажир имеет ровно один class trait: `basic`, `comfort` или `business`. Отдельного `serviceLevelId` нет. Class trait определяет selectors/logit modifiers и используется assessment для entitlement и относительных требований к скорости/качеству. Он не запрещает запрос вне entitlement.

NPC используют общую модель `traits + actions + events`.

Для baseline достаточно небольшого набора traits, например:

```text
attentive
impatient
hungry
sleepy
angry
```

Trait одновременно является плоским состоянием/селектором и модификатором доступных действий/logits.

NPC action выбирается после hard filtering через stable softmax + deterministic RNG.

Запрос услуги выражается waiting action: например `request-drink` добавляет `waiting-drink` и ждёт события передачи напитка либо timeout. Отдельный `ServiceRequest` object baseline не требуется.

## 10. Диалоги

Dialogue не является отдельной domain state machine.

Client отображает server-provided interaction/actions как реплики или варианты ответа.

Конкретные тексты могут быть статическими ресурсами, подготовленными вручную или offline-инструментами.

## 11. Короткая смена

### PreDeparture / приёмка

Игрок начинает на исходном перроне. Пассажирского потока на этом этапе нет.

Журнал лежит в заданной точке перрона. Игрок должен:

1. взять журнал;
2. войти в вагон;
3. проверить связь, огнетушитель, климат-контроль, стоп-кран и санитарное состояние;
4. самостоятельно заполнить checklist;
5. вернуть журнал в исходную точку до дедлайна отправления.

Scenario задаёт `preDeparture.duration`. Некритические ошибки не обязаны технически блокировать отправление: они учитываются assessment. Критическая неисправность может завершить попытку ещё до выезда через terminal rule.

### Посадка на исходной станции

После `preDeparture` Scenario переходит к `originStop`. На этом этапе пассажиры начинают прибывать с исходного перрона, игрок проверяет документы и помогает с размещением.

Приёмка и посадка не смешиваются: к началу `originStop` журнал уже должен быть возвращён в исходную точку.

Для demo можно ориентироваться на окно порядка 25–30 минут до отправления, но конкретное значение является параметром Scenario.

### Поездка и остановки

После `originStop` и отправления Scenario выполняет упорядоченный `route.stops[]`.

Каждая остановка задаёт:

- `travelBefore` — время поездки от предыдущей точки;
- `dwell` — время стоянки;
- подключаемый platform region;
- число/параметры выходящих пассажиров;
- число/параметры входящих пассажиров.

На travel interval перрон отключён. На остановке он подключается как дополнительная область Level, двери/edges активируются, и passenger flow происходит физически через неё.

Для первого demo достаточно одного reusable platform region без анимации прибытия/отправления поезда.

### Работа с пассажирами

На остановках и в пути игрок взаимодействует с пассажирами, проверяет билет/паспорт и принимает server-authoritative решения. NPC используют общую модель `traits + actions + events`.


### Уровни обслуживания и сервисные окна

Текущий demo использует три уровня обслуживания:

```text
basic
  проезд
  информирование
  стандартное обслуживание

comfort
  всё basic
  напиток
  лёгкий набор питания

business
  всё basic
  питание
  напитки
  дополнительное обслуживание
```

Для более высокого класса требования к скорости и качеству реакции выше. Точные SLA/коэффициенты являются tuning-параметрами.

Запрос пассажира не обязан соответствовать его классу: такой запрос всё равно может возникнуть и должен получить корректную реакцию игрока.

Scenario задаёт `servicePlan` как временные окна, а не отдельные stages. Для текущего демонстрационного расписания ориентир:

| Время | Событие |
|---|---|
| 11:30–11:55 | посадка, проверка документов, размещение |
| 11:55–12:00 | завершение посадки и готовность |
| 12:00 | отправление |
| 12:00–12:10 | помощь после отправления |
| 12:15–12:45 | питание классов, где оно включено |
| 12:45–13:00 | постсервисное/текущее обслуживание; мусор не моделируется |
| 13:00–14:00 | текущее обслуживание и контроль вагона |
| 14:05 | подготовка к прибытию / информирование |
| 14:20 | прибытие и высадка |

Подробности — `implementation/service-levels.md` и `implementation/trip-service-plan.md`.

### Нештатная ситуация

Scenario вызывает минимум одно основное событие:

- пожар; или
- проблема давления/климатической системы; или
- иная критическая неисправность.

Попытка может завершиться раньше штатного конца маршрута. Например:

- корректное применение стоп-крана в критической ситуации завершает рейс, но может считаться хорошим решением по безопасности;
- невосстановимое повреждение вагона/корпуса завершает попытку;
- критическая неисправность, обнаруженная на приёмке, может сделать отправление невозможным.

Terminal reason и assessment разделены: факт раннего завершения сам по себе не означает низкий safety score.

### Завершение

Baseline не требует отдельного этапа финальной сдачи/уборки.

Simulation формирует:

- safety score;
- customer satisfaction score;
- achievement IDs;
- canonical replay source (`versions + seed + user inputs`);
- terminal outcome/reason.

Game Server отправляет результат Platform Server.

## 12. Guided и replay

Тот же baseline должен работать в режимах:

```text
live
guided
replay
```

Guided может выдавать transient hint events.

Replay запрещает gameplay input, воспроизводит тот же run и может раскрывать дополнительную диагностику через protocol extensions/on-demand inspection.

## 13. Что сознательно не входит в baseline

Не требуется:

- несколько типов вагонов;
- весь поезд;
- многослотовый inventory;
- физически точная CFD/термодинамика;
- сложная модель распространения пожара;
- большое число пассажиров;
- универсальная workflow engine;
- runtime LLM;
- сложная социальная симуляция;
- полноценный редактор уровня;
- обязательный reversible event log.

## 14. Конкретная визуальная реализация

Client-side asset composition описана в `implementation/`.

Особенно важно:

- персонажи собираются из манекена и слоёв одежды;
- огнетушитель имеет отдельные слои чеки, стрелки манометра и повреждения;
- стоп-кран имеет отдельную ручку и пломбу;
- билет, паспорт и журнал содержат программно вставляемый текст;
- один domain object может иметь world, held и modal representation.

## 15. Итоговый scope

Первый baseline должен доказать:

1. authoritative server-side movement/actions работают в едином мире;
2. client умеет отображать server-controlled layered objects и close-up UI;
3. журнал связывает осмотр мира с самостоятельным решением игрока;
4. документы и пассажиры используют тот же action framework;
5. переносимый огнетушитель связывает world item, held state и пожар;
6. короткая смена заканчивается оценкой, achievements и воспроизводимым replay source.
