# WebSocket-контракт игрового клиента, версия 1

Точный типовой источник: `Game/src/client/protocol.ts`. Пример dev-эндпоинта:
`Game/dev/demo-server.ts` на `/game-ws`. Его сценарии существуют только при
`vite serve`; production bundle импортирует лишь клиентские типы, транспорт,
`GameScene` и её менеджеры. Адрес настоящего эндпоинта задаётся через `VITE_GAME_WS_URL` при
сборке или через `<meta name="game-websocket" content="wss://…">` в оболочке.
Защита авторизации/сессии при реальной интеграции определяется сервером и
оболочкой; текущий dev-стенд локальный и не предоставляет production-аутентификацию.

## Открытие и восстановление

После WebSocket `open` клиент отправляет:

```json
{"type":"hello","protocolVersion":1}
```

Если у него уже есть `sessionId`, он передаёт его в `hello`. Сервер должен
вернуть полный `snapshot` с **текущим** наблюдаемым состоянием, даже если клиент
запрашивал resume. Если восстановление невозможно, сервер создаёт новую
сессию и присылает snapshot с новым `sessionId`. Неподтверждённые команды после
разрыва клиент не воспроизводит: сервер мог применить их до обрыва. Новый
snapshot устраняет неоднозначность. После восьми неудачных попыток клиент
показывает состояние failed; повторный запуск подключения должен быть доступен
пользователю.

При пропуске дельты или некорректном сообщении клиент блокирует команды и
отправляет:

```json
{"type":"resync","protocolVersion":1,"sessionId":"demo-1","afterRevision":12}
```

Сервер отвечает полным snapshot. Нельзя продолжать последовательность со
следующей дельты, если ревизия была пропущена.

## Публичное состояние

Минимальный пример полного сообщения:

```json
{
  "type": "snapshot",
  "protocolVersion": 1,
  "state": {
    "sessionId": "demo-1",
    "revision": 1,
    "simulationTime": 0,
    "phase": "boarding",
    "playerZone": "platform",
    "message": "Началась посадка.",
    "poi": [{
      "id": "panel", "kind": "panel", "label": "Панель давления",
      "zoneId": "cabin", "actions": [
        {"id":"quick","kind":"inspect","label":"Быстрый осмотр","enabled":true},
        {"id":"full","kind":"inspect","label":"Подробный осмотр","enabled":true}
      ]
    }],
    "npcs": [{
      "id": "p2", "label": "Мария", "zoneId": "cabin", "anchorId": "seat-2",
      "intent": {"kind":"sit","targetId":"seat-2","sequence":1},
      "actions": [{"id":"talk","kind":"talk","label":"Поговорить","enabled":true}]
    }],
    "cues": [], "tasks": [], "dialogue": null, "item": "stored",
    "metrics": null, "debrief": null
  }
}
```

Все массивы в полном snapshot обязательны, даже пустые; `dialogue`, `metrics`
и `debrief` передаются как `null`, когда недоступны. `controls` опционален и
предназначен лишь для серверов, поддерживающих паузу/ускорение. Поля
`simulationTime`, `softDeadline` и `hardDeadline` измеряются в игровых секундах
от начала сессии. Положительная `revision` увеличивается на единицу для
каждой публичной дельты. После restart можно отправить новый `sessionId` с
начальной ревизией; dev-стенд также допускает полный snapshot той же сессии с
сброшенной ревизией.

`poi` перечисляет только видимые объекты и доступные сейчас действия. Для
объекта после осмотра сервер может добавить строку `observation`; быстрый и
полный осмотр дают разную точность. NPC передаётся с логической зоной,
начальным `anchorId` и видимым intent. `sequence` intent меняется при новом
намерении; клиент строит маршрут и анимацию к `targetId`. `speech` — фоновая
реплика. Латентные traits, utility, knownFacts, скрытая клетка повреждения,
будущие события, RNG, точные баллы до раскрытия и серверный журнал **не
входят** в сообщение.

`cues` показывают наблюдаемые признаки: `speech`, `call`, `whistle`, `pressure`,
`smoke`, `fire`, `notice`. `anchorId` добавляется только если источник уже
обнаружен; общий свист давления в стенде не содержит координат пробоя.
`sourceId` у обращения указывает на уже видимого NPC и позволяет подойти к
нему для разговора. Его не следует использовать для скрытого источника аварии.

`tasks` существуют независимо от `dialogue`: `sourceId`, `targetId`,
`urgency`, `softDeadline`, `hardDeadline`, `state` (`open/completed/failed`) и
доступные действия. Клиент интерполирует оставшееся время для HUD, но никогда
не меняет состояние задачи или оценку по локальным часам.

`dialogue` содержит `id`, `npcId`, заголовок, строки, уровень 1 или 2 и до
трёх вариантов ответа. `document`/`ticket` появляются только если сервер
разрешил их наблюдение. Для уточнения сервер присылает новый DialogueView с
изменёнными фактами/ответами. Клиент не перебрасывает варианты сам.

`metrics` содержит два **показанных сервером** числа: `safety` и
`satisfaction`; `debrief` — серверные строки процесса и фактического исхода.
Клиент не вычисляет ни одно из этих значений.

## Дельты и ответы на команды

Вместо полного snapshot сервер обычно присылает:

```json
{"type":"delta","protocolVersion":1,"sessionId":"demo-1","revision":2,
 "patch":{"simulationTime":8,"message":"Слышен свист.",
          "cues":[{"id":"whistle-1","kind":"whistle","text":"Слышен слабый свист."}]}}
```

В `patch` передаются только изменённые публичные поля. Списки (`poi`, `npcs`,
`cues`, `tasks`) при наличии заменяются целиком, а не неявно сливаются. `null`
очищает модальное состояние/оценку; отсутствие ключа оставляет прежнее
значение. Дельты принимаются только строго `current.revision + 1` и при том
же `sessionId`. Устаревшие дельты игнорируются; разрыв вызывает resync.

Команда содержит `requestId`, `baseRevision` и семантический тип:

```json
{"type":"command","protocolVersion":1,"sessionId":"demo-1",
 "requestId":"demo-1:4","baseRevision":12,"kind":"inspect",
 "targetId":"panel","inspection":"full"}
```

Поддерживаемые типы: `move-zone`, `inspect`, `interact`, `talk`,
`dialogue-choice`, `take-item`, `use-item`, `report`, `complete-task`, `finish`.
`dev-control` доступен только в тестовом стенде (вариант сценария в `optionId`
или `speed` 0/1/3). `move-zone` несёт `zoneId`; `dialogue-choice` — `optionId`;
`inspect` — `inspection` `quick/full`; остальные передают смысловой `targetId`.
Клиент не отправляет каждый кадр, путь, пиксельные координаты, рассчитанный
результат или скрытые факты.

Сервер отвечает `ack` с `requestId` и ревизией результата либо `reject` с
читаемой причиной. Ack **не заменяет** дельту: UI показывает результат только
после публичного обновления. Сервер должен помнить обработанные requestId в
сессии и не применять повтор дважды. При reject состояние мира не меняется,
а интерфейс показывает причину. Сервер проверяет зону, минимально возможное
время перехода, достижимость объекта, состояние предмета/диалога и правила
действия. Он не воспроизводит точный Phaser pathfinding.

## Локальные сценарии и ограничения

`npm run dev` поднимает отдельный `/game-ws`; ветки `pressure`, `fire`,
`service`, `conflict` выбираются в dev UI. Тестовый сервер демонстрирует
публичный контракт и несколько ответов/исходов, но не заменяет полноценную
серверную NPC-utility, скрытую сетку или нормативную симуляцию. Инвентарь
сюжетов и различие между реализованным стендом и общим UI указаны в
`dataset-scenario-map.md`.
