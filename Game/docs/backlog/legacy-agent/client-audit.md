# Аудит клиента перед переходом на серверное состояние

Проверено на `feature/mechanics-playground` до реализации клиентского goal.
Источники: `src/main.ts`, доменные модули и тесты, `vsm_game_mechanics_design.md`.

| Поведение | На ветке сейчас | Что сохранить | Действие для целевого клиента |
| --- | --- | --- | --- |
| Клик и движение между перроном и вагоном | Прямые точки и переход через дверь | Управление кликом, понятная цель, ходьба | Изометрическая геометрия, маршрут вокруг мебели, зоны и локальные координаты |
| Пассажир и посадка | Один пассажир, расписание и документ | Сопоставление билета и документа, диалог | 3–5 видимых NPC, маршрут по присланному intent; документы только после серверного наблюдения |
| Диалог | Статические варианты, локальные эффекты | Читаемые реплики и явное решение | До трёх ответов, два уровня, уточнение и подтверждение сервером |
| Осмотр панели | Быстрый и подробный, локальное давление | Две глубины осмотра и различимое показание | Только присланные признаки и доступные действия |
| Огнетушитель/пожар | Локальный предмет, таймер пожара и исход | Понятные состояния предмета и реакция на инцидент | Состояния и исход приходят с сервера; клиент рисует эффекты |
| Время и итог | Локальный `world`, `assessment` | HUD, пауза/ускорение в стенде, объясняющий итог | Время и оценка авторитетны на сервере; в клиенте только интерполяция HUD |
| Задачи/запросы | Нет отдельной сущности | — | Отдельный список с источником, сроками и состоянием |
| Сеть | Нет | — | Версионируемый WebSocket-контракт, snapshot/delta, ack/reject, resync |
| Визуальный мир | Серые примитивы 2D | Читаемые подписи/подсказки | Собственные растровые спрайты и изометрия 2.5D |
| Сценарии | Один жёсткий маршрут | Работающие тесты доменных модулей как исторический ориентир | Отдельные воспроизводимые pressure/fire/service/conflict пробы через dev-сервер |

`world.ts`, `passenger.ts`, `systems.ts`, `incident.ts`, `equipment.ts`, `dialogue.ts`,
`assessment.ts` и их тесты описывают прежний локальный полигон. Они не должны
импортироваться production entry point после перехода. Удалять их сразу нельзя:
сначала нужно сохранить соответствующие клиентские сценарии и проверить их
через новый контракт. В production bundle не должно быть скрытого состояния или
кода, который вычисляет итог.
