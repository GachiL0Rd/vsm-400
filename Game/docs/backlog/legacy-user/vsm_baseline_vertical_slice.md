# Baseline: первый играбельный вертикальный срез симулятора проводника ВСМ

**Статус:** минимальный технический baseline для начала реализации

**Назначение:** зафиксировать наименьший объём систем и контента, который уже позволяет полностью пройти короткую смену и проверить основной игровой цикл.

Baseline является подмножеством общей концепции из `vsm_conductor_game_concept.md`. Его задача — не показать все функции будущего демонстрационного решения, а доказать, что единый 2D-мир, контекстные взаимодействия, осмотр объектов, пассажиры, время и последствия работают вместе как одна игра.

## 1. Критерий готовности baseline

Baseline считается рабочим, если игрок может пройти короткую смену целиком:

1. появиться на перроне;
2. войти в назначенный вагон;
3. выполнить несколько действий приёмки;
4. начать посадку;
5. принять 2–3 пассажиров через диалог и проверку документов;
6. доложить о готовности и начать поездку;
7. выбирать точки перемещения по вагону кликом во время движения;
8. столкнуться минимум с одной технической или пожарной ситуацией;
9. корректно либо некорректно обработать её и получить последствия;
10. завершить поездку, выполнить финальную проверку и получить краткий результат смены.

Для baseline достаточно одного короткого сценария с небольшим числом случайных вариаций.

## 2. Пространство

Используются две основные локации:

- **перрон** — начало смены, подход к вагону, посадка и финальный выход;
- **вагон** — основная игровая зона с пассажирским салоном, служебной частью и туалетом.

Геометрия обеих локаций статическая. Каждый элемент окружения привязан к заранее
заданному месту, но его вид, доступные действия и последствия меняются вместе с состоянием.
Процедурно изменяются именно эти состояния, пассажиры и отдельные события, а не планировка мира.

В базовой модели по миру перемещаются игрок, NPC и переносимые ими предметы. Двери, панели, датчики,
места хранения и другие элементы не являются свободно движущимися сущностями. Анимация изменения
состояния не меняет эту модель.

Внутри вагона для baseline достаточно нескольких функциональных зон:

- вход/дверь;
- пассажирские места;
- зона проводника/место ожидания;
- туалет;
- место хранения огнетушителя;
- несколько точек технического осмотра.

## 3. Базовое управление и взаимодействие

Игрок умеет:

- задавать точку перемещения по 2D-миру кликом;
- видеть доступные контекстные действия рядом с объектами и NPC;
- выполнять простое действие непосредственно в мире;
- открывать детальный point-and-click осмотр объекта;
- держать один активный предмет в руке;
- начать диалог;
- доложить по связи;
- ждать и ускорять игровое время.

Baseline не требует полноценного инвентаря. Состояние `HeldItem` может содержать только один объект или `None`.

Детальный осмотр — это статическое увеличенное представление конкретного объекта. В нём клик по
заранее заданному элементу выполняет доступное в текущем состоянии действие. Свободная физическая
манипуляция, перетаскивание деталей или поиск произвольной точки воздействия не требуются, если их отдельно
не потребует конкретная механика.

## 4. Минимальный набор интерактивных объектов

### 4.1. Датчик/индикатор состояния давления

Объект нужен для демонстрации технического осмотра и сценария нарушения герметичности.

Минимальные свойства:

- состояние: `Normal / Warning / Fault`;
- обнаружено игроком: `bool`;
- доложено: `bool`.

Быстрый осмотр показывает общее состояние. Детальный осмотр может давать более точный признак неисправности.

Это игровая абстракция: baseline не моделирует физику давления высокоскоростного состава.

### 4.2. Огнетушитель

Минимальные свойства:

- исправность: `Normal / Fault`;
- положение: `Stored / Held`;
- готовность: `Safe / Prepared`.

Быстрый осмотр позволяет понять общее состояние. Детальный осмотр показывает ключевые элементы вроде пломбы/индикатора в упрощённом виде.

Ключевая последовательность:

`Stored → Held → Prepared → применение`

Подготовка выполняется именно через детальное взаимодействие с огнетушителем в руке, а не глобальной кнопкой.

Если игрок пытается тушить пожар неподготовленным огнетушителем, действие не выполняется и игра явно сообщает причину, например: **«Рукоятка не поддаётся — огнетушитель не подготовлен»**.

### 4.3. Туалет

Для baseline туалет является отдельной небольшой зоной, которая может:

- содержать источник утечки;
- содержать пожар;
- быть местом, куда заходит пассажир;
- содержать одну-две дополнительные интерактивные точки.

Сложная санитарная симуляция не требуется.

## 5. Упрощённая система герметичности/давления

Механика строится по принципу простой зональной системы, близкой по читаемости к системам кислорода/пожаров в FTL, но не претендует на физическую точность.

У каждой значимой зоны может быть состояние утечки:

- `None`;
- `Minor`;
- `Major`.

У вагона существует интерпретируемое общее состояние давления/герметичности:

- `Normal`;
- `Unstable`;
- `Critical`.

Утечка в зоне постепенно влияет на общее состояние. Для baseline достаточно простого правила по времени без моделирования потоков воздуха.

Состояние может проявляться через несколько каналов:

- показание датчика;
- характерный свист в конкретной зоне;
- реплику пассажира о заложенных ушах;
- самостоятельное обращение внимательного пассажира.

Таким образом одна проблема может быть обнаружена как через предмет, так и через NPC.

## 6. Упрощённая система пожара

Для baseline пожар является заранее определённым сценарием, а не полноценной физической симуляцией.

Зона имеет состояние:

- `NoFire`;
- `Fire`;
- `Extinguished`.

Допустимо добавить простой таймер ухудшения или переход в критический исход при полном игнорировании, но распространение огня между объектами для baseline не требуется.

Основная проверяемая механика:

1. обнаружить пожар;
2. при необходимости доложить;
3. взять огнетушитель;
4. детально подготовить его;
5. подойти к очагу;
6. применить подготовленный огнетушитель.

## 7. Диалоги и проверка документов

Диалоговая система используется при посадке и для простых обращений пассажиров в пути.

Во время посадки окно взаимодействия содержит одновременно:

- диалог;
- билет пассажира;
- документ, удостоверяющий личность.

Baseline требует только нескольких видов проверки:

- данные совпадают;
- данные не совпадают;
- пассажир задаёт простой вопрос или поясняет ситуацию.

Игрок выбирает готовые действия/ответы. Все реплики являются статическими ресурсами игры.

Локальная LLM может использоваться **вне runtime** для пакетной генерации вариантов этих ресурсов из шаблона ситуации, архетипа и нужного намерения. Для самого первого baseline допустимы и вручную подготовленные тестовые реплики: важно проверить формат ресурса и работу системы, а не качество генератора контента.

## 8. Пассажиры

В одной смене достаточно 2–3 пассажиров.

Каждый пассажир имеет минимальный набор явно интерпретируемых свойств.

### Внимательность

Например:

- `Low`;
- `Normal`;
- `High`.

Она влияет на:

- шанс заметить техническое или необычное состояние;
- шанс самостоятельно обратиться к проводнику;
- подробность сообщения о замеченной проблеме.

Пример: внимательный пассажир при нарушении герметичности скорее скажет, где именно услышал свист и когда почувствовал изменение; невнимательный может только случайно упомянуть, что «закладывает уши», либо вообще ничего не сообщить.

### Настроение

Например:

- `Calm`;
- `Neutral`;
- `Irritated`;
- `Stressed`.

Настроение влияет на:

- тон выбранного статического диалога;
- небольшие модификаторы вероятностей поведения;
- вероятность жалобы или повторного обращения.

Baseline не требует сложной социальной симуляции или взаимодействия пассажиров друг с другом.

### Поведение

NPC выбирает действие из небольшого набора доступных сейчас действий с весами, зависящими от состояния и свойств пассажира.

Примеры:

- сидеть;
- пройти в туалет;
- осмотреть доступный объект;
- обратиться к проводнику;
- упомянуть замеченную проблему;
- проигнорировать проблему.

Редкие действия могут иметь очень низкий базовый вес и усиливаться характеристиками/архетипом. Полная универсальная AI-система для baseline не требуется.

## 9. Интерпретируемые численные состояния

Численные параметры не должны существовать только как «сырой float», если их значение используется контентом, UI или генератором диалогов.

Предпочтительны два варианта:

1. enum с понятной семантикой;
2. число + обязательная функция интерпретации в именованный диапазон.

Например:

```text
AttentionScore = 0..100
InterpretAttention(score):
    0..24   -> Low
    25..74  -> Normal
    75..100 -> High
```

В игровой логике можно использовать число, но генератор диалога и интерфейс получают уже `Low / Normal / High`.

То же правило желательно применять к:

- настроению;
- тяжести проблемы;
- заметности;
- уровню риска;
- состоянию удовлетворённости пассажира.

Это упрощает статические ресурсы и не привязывает тексты к конкретным численным порогам.

## 10. Короткая смена baseline

Минимальный сценарий может выглядеть так:

### Приёмка

Игрок появляется на перроне и получает несколько минут до посадки. В вагоне доступны датчик давления, огнетушитель, туалет и несколько точек быстрого осмотра.

Один объект может иметь скрытое отклонение.

### Посадка

К вагону подходят 2–3 пассажира. Игрок последовательно начинает диалог, просматривает билет и документ и принимает решение.

Один пассажир может содержать простое отклонение в документах или дополнительный вопрос.

### Отправление

Игрок докладывает о готовности. После этого поезд начинает движение.

### Поездка

Игрок свободно двигается, ждёт, ускоряет время и взаимодействует с пассажирами/объектами.

В сценарии происходит одно основное событие:

- утечка/проблема герметичности; **или**
- статический пожар.

Дополнительно пассажир может заметить или не заметить признаки события в зависимости от внимательности.

### Завершение

После короткого периода движения поезд прибывает. Пассажиры выходят, игрок выполняет финальную проверку/доклад и получает краткий результат.

## 11. Упрощённая смена и отключение этапов

Сценарий должен уметь явно отключать ненужные этапы, чтобы разработчик или демонстрационный режим могли проверять отдельную часть игры без обязательного прохождения всего цикла.

Например:

```text
ReceptionCheck = Enabled
Boarding        = Disabled
Ride            = Enabled
FinalCheck      = Disabled
```

Отключённый этап:

- не проигрывается;
- его необходимые изменения состояния применяются автоматически;
- мир переводится в корректное стартовое состояние следующего этапа;
- этап не создаёт штрафов и не входит в расчёт оценки.

Внутренне полезно обозначать такое состояние как `AutoResolved` или `NotEvaluated`, а не как фактически успешно выполненное игроком. В интерфейсе демонстрационной сборки его можно просто скрывать.

Это позволяет, например, запускать только «посадка → поездка» или непосредственно тестировать пожарный сценарий.

## 12. Минимальная оценка результатов

Baseline не требует полной системы компетенций, но уже должен различать:

- что игрок сделал правильно/неправильно;
- что фактически произошло в мире.

Для каждого проверяемого события достаточно хранить:

- обнаружено ли оно;
- требовался ли доклад;
- был ли доклад;
- было ли выполнено правильное действие;
- фактический исход.

Таким образом пропущенная неисправность остаётся ошибкой даже в случае, когда случайное развитие ситуации не привело к тяжёлым последствиям.

## 13. Что сознательно не входит в baseline

Не требуется:

- несколько типов вагонов;
- весь состав;
- сложный инвентарь;
- полноценная физика давления;
- распространение пожара по сложной модели;
- медицинская система;
- сложные пассажирские конфликты;
- социальная симуляция пассажиров между собой;
- большое число документов и правил посадки;
- runtime-LLM;
- полноценный генератор диалогов как обязательная часть первого запуска;
- сложный backend;
- таблица лидеров;
- метапрогрессия;
- визуально завершённый UI.

## 14. Минимальные сущности данных

Для начала достаточно нескольких простых типов.

### `Interactable`

- `type`;
- `state`;
- `availableActions`;
- `detailedInspectionAvailable`.

### `Item`

- `type`;
- `condition`;
- `heldState`;
- `preparedState`.

### `Passenger`

- `attention`;
- `mood`;
- `currentAction`;
- `noticedFacts`;
- `ticketState`;
- `documentState`;
- `dialogueResource`.

### `Zone`

- `type`;
- `leakState`;
- `fireState`.

### `Shift`

- `time`;
- `phase`;
- `phaseConfiguration`;
- `heldItem`;
- `knownProblems`;
- `reportedProblems`;
- `evaluationFlags`;
- `outcomes`.

Не следует заранее строить универсальную ECS/DSL/сложную схему сценариев только ради baseline. Структуры можно расширять после появления первого полностью проходимого рейса.

## 15. Итоговый scope

Первый baseline должен доказать пять вещей:

1. **Мир:** игрок кликом выбирает точки перемещения между перроном и вагоном.
2. **Интеракции:** один и тот же механизм поддерживает быстрые действия и детальный осмотр.
3. **Люди:** 2–3 простых пассажира могут проходить посадку, разговаривать и вероятностно реагировать на мир.
4. **Состояние:** одна техническая система и один пожарный сценарий дают наблюдаемые последствия и позволяют применить предмет.
5. **Цикл:** короткая смена начинается, проходит через выбранные этапы и заканчивается итоговой оценкой.

После этого уже имеет смысл расширять не архитектуру целиком, а конкретный контент: дополнительные объекты, события, архетипы, документы, достижения и серверную статистику.
