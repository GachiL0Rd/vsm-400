# Процесс разработки

## Веточная модель

```text
feature/* ─┐
fix/*     ─┼─> dev ──> main
docs/*    ─┤
chore/*   ─┘
```

- Работа начинается от актуальной `dev`.
- Ветка решает одну обозримую задачу и возвращается в `dev` после собственной
  проверки.
- `dev` допускает незавершённое развитие продукта, но не заведомо сломанную
  сборку.
- `main` обновляется только в устойчивой точке, пригодной для запуска и
  демонстрации.

## Проверки

Каждый модуль владеет своими командами установки, запуска и проверки. Они
указываются в локальных `README.md` и `AGENTS.md`; при наличии модульного
`justfile` его рецепты являются только необязательными сокращениями.

Перед переносом `dev` в `main` необходимы:

1. чистая установка зависимостей;
2. полный `verify` каждого существующего модуля;
3. production-сборка;
4. запуск приложения и smoke-проверка основного сценария;
5. отсутствие случайных generated-файлов и секретов в Git.

## CI

Корневой workflow запускается на Windows для pull request и изменений в `dev`
и `main`. Каждый подпроект получает независимый job, вызывающий его собственную
проверку. При появлении нескольких модулей добавляется отдельный межмодульный
gate; существующие модульные проверки не заменяются E2E-тестом.

## Передача работы

В pull request или сообщении передачи укажите сделанное, точные выполненные
команды, их результат и известные ограничения. Исторический `PROGRESS.md`
перенесён в `docs/backlog/` и больше не обновляется после каждой задачи.
