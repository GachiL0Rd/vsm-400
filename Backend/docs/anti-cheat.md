# Античит

Учебная смена. Защищаем учёт очков и воспроизводимость итога, не чемпионат.
Модель угрозы: игрок подменяет клиент, повторяет ключ запуска, присылает
готовый итог.

## Сервер решает

Клиент очки не присылает. Ход считает Game Server. Backend принимает итог
только от Game Server: `POST /api/game/sessions/{attemptId}/finish`,
Bearer `GAME_SERVER_TOKEN`, один раз на сессию `ACTIVE`. Повтор того же тела —
тот же `resultId`. Другое тело после `COMPLETED` — 409 `result-conflict`.

Коды ачивок из итога Backend не начисляет. Очки пишет обработчик
`run.completed`.

Повтор того же `runId` не делает второй `ZINCRBY`. Два писателя рейтинга
считаются ошибкой устройства, не гонкой «на потом».

Дольше 80 решений или шкала вне 0..100 делает рейс подозрительным в
`RunRecorder`: очки ноль, список решений режется до 80. Офлайн-копия полного
графа с дельтами в браузере равнялась бы решателю на телефоне; кабинет её
не раздаёт.

## Срок попытки

`expiresAt` на `GameSession`. Раз в минуту просроченные `PENDING` и `ACTIVE`
становятся `EXPIRED`. `finish` после этого — 404 `attempt-not-found`.
Часы телефона срок не двигают. Дедлайны задач внутри смены считает Game Server.

## Билет

JWT билета: `aud=vsm-game`, `sid`, `jti`, срок 2 минуты, подпись
`GAME_TICKET_SECRET`. Access-JWT кабинета на сокет не вешается. Билет уходит
в `launchUrl` (`sessionKey`), не в cookie.

Одноразовость: успешный `resolve` делает `SET vsm:ticket:<jti> NX EX`.
Второй `SET` не проходит. Повтор билета — 410 `session-consumed` и флаг
`ticket-reused`. Повторный `POST /api/v1/game-sessions` на открытую смену
отдаёт ту же сессию и новый билет: `resolve` с ним проходит.
См. `game-server-contract.md`.

Украденный билет живёт до `exp` или до первого `resolve`. Выход из кабинета
билет не гасит и сокет Game не закрывает.

## Seed

Seed смены — `crypto.randomBytes(32)` на сервере в момент открытия.
Клиенту уходит `seedCommit = sha256(seed)` (hex). План смены —
детерминированный HMAC-SHA256 от этого seed и счётчика (SPEC §5, `rng.ts`).
Тот же seed и счётчик дают тот же план. Seed лежит в `seedEnc`
(AES-256-GCM, ключ `SEED_ENC_KEY`). Публичной ручки раскрытия нет.
Разбор рейса seed не отдаёт.

Это связывает план с обязательством, которое опубликовано в начале рейса.
Оператор, который сам выбирает seed до публикации commit, может перебирать
его заранее. Схема держит игрока, не честность оператора против самого себя.

`Math.random` для параметров смены не используется.

## Флаги и рейтинг

На `GameSession.flags`. В `Run.suspicious` из флагов сессии попадает только:

- `ticket-reused` — повтор уже погашенного билета.

`reaction-fast`, `decision-after-deadline` и `seq-jump` больше не пишутся:
ход смены Backend не принимает. Старая строка с `reaction-fast` сама по себе
рейс подозрительным не делает.

Повторный `POST /api/v1/game-sessions` при своей открытой смене возвращает её
и пишет `session.resumed`. Флага за это нет: вторая смена под тем же advisory
lock не создаётся.

Подозрительный рейс сохраняется, очки в ZSET рейтинга не идут. Снимает
человек: `POST /api/v1/runs/:id/review`, тело `{ "approve": true }` или
`false`. Вызывает CHIEF бригады игрока, но не на свой рейс, или ADMIN.
`approve: true` снимает подозрение. Ручку пишет контур прогрессии, не сессии.

Логин ограничен по частоте (счётчик в Redis). Ответ на чужой и на неверный
пароль один: «неверный логин или пароль». Тело запроса API — не больше 1 МиБ.
Частота кадров сокета — забота Game Server. Число «столько-то команд в
секунду» SPEC не фиксирует.

## Чего это не закрывает

Отдали телефон коллеге, зашли под одним логином, прошли смену руками.
Организаторы вынесли это за модель угрозы: общий аккаунт не считается
взломом тренажёра.

Не закрывает и бота, который играет допустимыми командами на Game Server.
Сервер отличает повтор билета и повтор итога, не «человека от скрипта с
верными ответами».
Компрометация Game Server, Postgres или `GAME_SERVER_TOKEN` вне этой модели:
сервисный токен — доверие контура, не пользовательский пароль.

## bcrypt — не генератор случайных чисел

bcrypt здесь не источник случайности и не механизм seed.

В OpenBSD `bcrypt.c` генератор вызывается один раз в `bcrypt_initsalt`:
16 байт соли через CSPRNG libc (`arc4random_buf`). `bcrypt_hashpass` при тех
же пароле, соли и cost всегда даёт тот же выход, иначе проверка пароля
невозможна. Пароль схемы 2b обрезается на 72 байтах. Вызов специально
медленный: это один детерминированный блок, не счётчик и не поток.
Повтор hash с той же солью не новый рандом.

Непредсказуемость рейса делает `randomBytes`, не хеш пароля. Пароли учёток
хранятся argon2id (SPEC §1). bcrypt для новых паролей не заводится: у него
тот же потолок 72 байта и нет задачи, которую argon2id здесь не закрывает.
